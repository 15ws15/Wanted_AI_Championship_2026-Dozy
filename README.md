# Dozy

시작하기 어려운 할 일을, 지금 5분 안에 할 수 있는 하나의 행동으로 바꿔주는 웹 서비스.

**→ [wanted-ai-championship-2026-dozy.vercel.app](https://wanted-ai-championship-2026-dozy.vercel.app)**

원티드 AI 챔피언십 2026 출품작. 설치 없이 바로 열립니다.

---

## 왜 만들었나

할 일을 알고 있는데도 시작하지 못하는 상태가 있다. 원인은 게으름이 아니라 **첫 스텝이 막연한 것**이다.

"보고서 작성"이라는 한 줄은 머릿속에서 30단계짜리 덩어리로 느껴진다. 덩어리가 클수록 착수 비용이 커지고, 착수 비용이 크면 미룬다.

기존 투두앱은 이 덩어리를 **그대로 체크박스 하나로 만든다.** 관리는 되지만 시작은 여전히 안 된다.

|  | 기존 투두앱 | Dozy |
|---|---|---|
| 핵심 기능 | 우선순위 / 마감일 / 카테고리 관리 | 착수 장벽 낮추기 |
| "보고서 작성"에 대해 | 체크박스 1개 | "제목 후보 3개 적기" |
| 사용자가 막혔을 때 | 도와줄 방법 없음 | 더 잘게 쪼개기 |
| 뭐부터 할지 모를 때 | 정렬 기준 제공 | 목록 전체를 보고 추천 |

## 핵심 기능

### 1. 막힘의 종류를 구분해서 쪼갠다

이 서비스에서 가장 많은 시간을 쓴 부분이다. 처음에는 "가장 작은 물리적 동작"을 뽑게 했는데, 써보니 **동기부여가 되지 않았다.**

> "보고서 작성" → "빈 한글 파일 열기"

틀린 답은 아니다. 하지만 하고 나도 아무것도 남지 않고, 애초에 미루게 만든 **그 빈 화면**을 마주할 뿐이다.

막힘에는 두 종류가 있고 처방이 다르다는 것을 여기서 알았다.

| 할 일의 성격 | 막고 있는 것 | 맞는 첫 행동 |
|---|---|---|
| 운동, 청소, 설거지 — 뭘 할지는 이미 아는 일 | **몸** | 준비 동작 → "운동복 바지만 먼저 입기" |
| 보고서, 발표자료, 공부 — 뭘 할지가 흐린 일 | **막막함** | 흔적이 남는 행동 → "제목 후보 3개 적기" |

지금은 모델이 먼저 어느 쪽인지 판단한 뒤 답을 만든다. 측정 결과는 아래 "프롬프트를 어떻게 다듬었나"에 있다.

### 2. 막히면 계속 더 잘게 쪼갠다

제시된 행동조차 버거울 수 있다. `이것도 어려워요`를 누르면 **그 행동의 바로 직전 단계**를 다시 만든다.

```
운동하기
  └ 운동복 바지 입기
      └ 침대에 앉아서 바지 한쪽 다리 밀어넣기
          └ 침대에 앉아 양손으로 바지 허리띠 잡기
              └ 엄지손가락으로 바지 고리 하나 걸기
```

들여쓰기 깊이가 그대로 "얼마나 잘게 쪼갰는지"를 보여준다. 이 위계가 이 서비스의 시각 언어다.

첫 칸은 무언가를 만들어내는 행동이고, 그 아래 칸들이 준비 동작·자리 옮기기·파일 열기를 맡는다. 사다리의 위아래 역할이 다르다.

depth 3에서 멈춘다. 그 이상은 의미 없는 세분화이고, 무한 호출 경로가 된다.

### 3. 항목 하나가 아니라 목록 전체를 보고 추천한다

`뭐부터 할지 모르겠어요`를 누르면 미완료 목록 **전체**를 맥락으로 넘겨서 지금 가장 시작하기 쉬운 하나를 고른다.

```
이사 준비 / 전기요금 내기 / 운동 시작하기
  → 전기요금 내기 · "준비물 없이 바로 끝낼 수 있어요"

연말정산(마감 내일) / 대청소 / 우산 챙기기
  → 우산 챙기기 · "준비물이 적고 가장 쉬워요"
```

두 번째가 의도한 동작이다. **마감이 임박한 연말정산을 제치고 착수 비용이 가장 낮은 것을 골랐다.** 판단 기준의 우선순위가 `착수 비용 > 장애물 해제 > 마감 임박` 순이기 때문이다.

Dozy는 마감 관리 도구가 아니라 착수 도구다. 이 순서가 그 성격을 결정한다.

## 프롬프트를 어떻게 다듬었나

**[측정 기록 전문 → `docs/prompt-log.md`](docs/prompt-log.md)**

출력 품질이 이 서비스의 전부라서, 버전마다 서로 다른 유형의 할 일 10종을 같은 조건으로 넣고 사람이 판정했다. 다섯 번 고쳤고 그 과정에서 얻은 것들:

- **few-shot 예시를 목록으로 주면 안 된다.** `할 일 → 행동` 쌍을 나열했더니 모델이 답하는 대신 목록을 이어썼다. "방 청소"에 "메일함 열기"가 나오는 식이었다. 예시를 걷어내고 기준만 서술하자 10/10이 정답이 됐다.
- **thinking 토큰이 출력 토큰 예산을 공유한다.** 256으로 잡았더니 답이 문장 중간에서 잘렸고, 마지막 줄만 취하는 후처리가 추론 조각을 답으로 반환하고 있었다.
- **프롬프트의 어휘는 그대로 샌다.** "엉망이어도 되는"이라고 썼더니 출력에 "쓰레기 단어"가 섞여 나왔다.
- **품질 문제를 프롬프트 탓으로 돌리기 전에 입력이 온전히 도착하는지 확인해야 한다.** 한동안 원인을 잘못 쫓았는데, 범인은 측정 도구가 한글 본문을 깨뜨리고 있던 것이었다.

## 기술

| | |
|---|---|
| 프레임워크 | Next.js 16 (App Router) + TypeScript |
| 스타일 | Tailwind CSS v4 |
| LLM | Google Gemini `gemini-3.5-flash-lite` |
| 저장 | localStorage |
| 배포 | Vercel |

**API 키는 서버에서만 쓴다.** LLM 호출은 전부 Route Handler를 거치고, 클라이언트 번들에는 키도 SDK도 프롬프트도 들어가지 않는다. 배포본의 JS 청크를 전수 검사해 확인했다.

**계정도 DB도 없다.** 할 일은 브라우저의 localStorage에만 남는다. 저장된 값이 깨져 있어도 앱은 뜬다.

**의존성을 최소로 뒀다.** 상태 관리 라이브러리, UI 컴포넌트 라이브러리, 날짜 라이브러리, 캘린더 컴포넌트를 쓰지 않았다. 달력은 월간 그리드를 직접 그린다 — 1일의 요일만큼 앞을 비우고 그 달 날짜를 채우면 끝이라 라이브러리를 들일 이유가 없었다.

**날짜 비교는 전부 `YYYY-MM-DD` 문자열로 한다.** Date 객체 비교는 타임존 버그의 원인이다. 월말·연말 넘김이 깨지면 1월 31일에 "내일까지"가 영영 안 뜨므로 경계 검사를 남겨뒀다.

```bash
npm test
```

localStorage가 망가진 경우도 같은 방식으로 검사한다. 개발자도구에서 손으로 깨뜨려보는
확인을 코드로 옮긴 것이다 — 손으로 하면 다음에 또 잊는다. 깨진 JSON, 배열이 아닌 값,
항목 하나만 망가진 배열, 저장소 접근 자체가 막힌 환경까지 넣어두고 앱이 빈 목록으로
뜨는지 본다.

**공개 URL이라 rate limit을 걸었다.** IP 기준 시간당 30회. 무료 티어의 분당 한도에 걸리면 남은 대기 시간을 사용자에게 그대로 안내한다.

## 설계할 때 지킨 것

**관리가 아니라 착수가 목적이다.** 기능을 넣을지 고민될 때 기준은 하나였다 — "이게 사용자가 일을 시작하는 데 도움이 되는가?" 정렬 옵션, 태그, 반복 일정, 우선순위 라벨은 전부 관리 도구지 착수 도구가 아니라서 넣지 않았다.

**재촉하지 않는다.** 미루는 사람은 이미 스스로에게 압박을 받고 있다. 진행률 막대도, 연속 달성 일수도, 완료 축하 애니메이션도 넣지 않았다. "남은 일 3"처럼 사실만 조용히 적는다.

**AI가 죽어도 할 일 관리는 된다.** LLM 호출 실패, 응답 지연, 할당량 소진, localStorage 손상 — 모든 경우에 앱은 살아 있고 사용자가 읽을 수 있는 한국어 문장으로 상황을 알린다.
